ERROR 1 (MAIN, BLOCKING) — Simulink simulation target build failure
--------------------------------------------------------------------------------

SYMPTOM
  Any attempt to simulate a Simulink model containing the "Python Code" block
  (or otherwise needing to compile a simulation target) failed with:

      Problem creating simulation target for the model 'probe_py'.
      Error(s) encountered while building simulation target MEX-file
      for model 'probe_py'.
      'probe_py_cgxe.bat' is not recognized as an internal or external
      command, operable program or batch file.
      ### Build procedure for model: 'probe_py' aborted due to an error.

INVESTIGATION
  * The generated build script existed on disk:
      ...\slprj\_cgxe\probe_py\src\probe_py_cgxe.bat
    and its contents were valid (sets PATH/COMPILER and invokes gmake).
  * A MEX test compiled fine (MinGW64 gcc works), so the compiler itself
    was NOT the problem.
  * Manually executing the .bat reproduced the failure:
        cmd /c probe_py_cgxe.bat        ->  "not recognized"
        cmd /c .\probe_py_cgxe.bat      ->  WORKS
    i.e. batch files could NOT be resolved and executed from the CURRENT
    directory by bare name, but worked with an explicit path prefix (".\").

ROOT CAUSE
  The shell that launched MATLAB had the environment variable

      NoDefaultCurrentDirectoryInExePath=1

  set. When this variable is set, Windows (and cmd.exe) EXCLUDES the current
  directory from command resolution for names given without a path. MATLAB's
  Simulink build system internally does (effectively):

      cd <slprj>\_cgxe\<model>\src
      cmd /c <model>_cgxe.bat          <-- bare name, resolved from CWD

  which therefore failed in this environment. This is an environment quirk of
  the sandboxed tool harness used for this session, NOT a defect of the
  project, MATLAB, or Simulink.

FIX / WORKAROUND (used for all subsequent MATLAB batch launches in this
session)

      Remove-Item Env:NoDefaultCurrentDirectoryInExePath
      & "C:\Program Files\MATLAB\R2026a\bin\matlab.exe" -batch ...

  Note: a Simulink build can also fail when the model/build folders are on a
  mapped network drive; Simulink.fileGenControl('set','CacheFolder',<local>,
  'CodeGenFolder',<local>) is also set defensively in build scripts.

STATUS: RESOLVED — after the fix, a probe Simulink model with a Python Code
block simulated successfully and confirmed Simulink->Python data marshaling
(signals arrive in Python snippets as numpy.ndarray).

IMPACT ON THE PROJECT
  None for normal use. If you run MATLAB from a normal desktop/session (not
  this harness), the variable is not set and models simulate as usual. If you
  ever see "<model>_cgxe.bat is not recognized" again, check this variable.

ERROR 2 (MINOR) — MATLAB script parse error in run_planner_demo.m
--------------------------------------------------------------------------------

SYMPTOM
      Declaring a variable with the same name as the local function "ob"
      is not supported in scripts.

ROOT CAUSE
  A script-local variable named `ob` collided with the local helper function
  `ob(...)` defined at the bottom of the same script. MATLAB scripts (unlike
  function files) do not allow a variable to share a name with a local
  function.

FIX
  Renamed the variable to `obst` / `obst2`. Script then ran to completion.

ERROR 4 (BEHAVIORAL TUNING, NOT A DEFECT) — Pedestrian Crossing scenario
--------------------------------------------------------------------------------

  In the first MATLAB demo run, the "Pedestrian Crossing" validation scenario
  registered repeated collisions: the EGO correctly yielded and came to a
  full stop for the crossing pedestrian, but the pedestrian (moving at
  8 px/s on a straight analytic path) then walked INTO the stationary EGO.
  The existing safety gate only ever shortens the EGO's own motion - it never
  modifies obstacle trajectories, by design.

  FIX (validation-layer only): adjusted the scenario's pedestrian speed to
  10 px/s so the EGO yields, the pedestrian completes the crossing in front
  of the stationary EGO, and the EGO then resumes. Result: 0 collisions,
  0.92 m minimum clearance. No planner or simulation code was changed.

--------------------------------------------------------------------------------
ERROR 5 (CODE BUG, INTEGRATION LAYER ONLY) — run_everything ordering
--------------------------------------------------------------------------------

SYMPTOM
  When the MATLAB 5-scenario demo ran FIRST in the same MATLAB session, the
  subsequent Simulink validation froze: ego_log flat at the initial condition,
  planner_log all zeros, 0 replans.

ROOT CAUSE
  State bleed through the persistent InProcess Python module. The demo leaves
  matlab_bridge._SESSION.goal == (2500, 400) — identical to the Simulink
  model's goal — so the model's Python Code block skipped set_goal(). But the
  block's InitializeConditionsCode had already rebuilt a FRESH PathPlanner via
  initialize_planner(), and that reset did not clear the session goal. The
  fresh planner therefore had goal=None and returned empty paths.

FIX (matlab_bridge.py only — the original simulation code was untouched)
    a) initialize_planner()'s internal reset now clears the session goal
       (self.goal = None);
    b) plan_path() self-heals: if the planner's own goal differs from the
       session goal (fresh planner), it re-applies p.set_goal().

STATUS: RESOLVED — verified with run_everything (demos first, Simulink
second) producing a passing end-to-end Simulink run.
